# Research Questions

## Context

This is a Rust CLI that manages an `orksorksorks.toml` config file: `init_command` generates the file on first run, commands read it back for execution, and integration tests assert on the generated bytes. Relevant areas: `src/config.rs` (types, serialization, validation), `src/commands/mod.rs` (init flow), `src/config_dir.rs` (path resolution), `tests/` (init and config tests), the resolved `toml` crate dependency, and the user's live config file at `~/.config/orksorksorks.toml` (a symlink to a dotfiles repo file). Focus on what exists and how it works.

## Questions

1. How does the init command write the initial `orksorksorks.toml` end-to-end: routing from `Commands::Init`, destination path resolution (including `--config` and env overrides), the exact byte output produced by `toml::to_string` on `Config::default()`, the file write sequence, and how io errors are surfaced?

2. How does the crate parse and validate a config file when reading it back — `read_config`, `toml::from_str`, `Config::validate()`, and `deny_unknown_fields` — and what syntactic constraints does that parsing place on the file (comment lines, blank lines, key ordering, array-of-tables) for a hand-edited file to round-trip cleanly?

3. What does the resolved `toml` crate (1.1.5) support regarding comments — can any serializer API emit them, how are they treated on deserialization, and is any comment-capable crate (e.g. `toml_edit`) present? What commented TOML examples exist in the repo or its docs, and what style do they use?

4. What is the exact structure and content of the user's live config at `~/.config/orksorksorks.toml` (symlink target `/Users/vardy/dev/dotfiles/orksorksorks/orksorksorks.toml`): top-level keys, each `[[section]]` with its entries and fields, the full prompt set (incl. QRSPI prompts), any existing comments or formatting conventions, and how it maps onto the `Config` type?

5. How do the integration tests exercise `init` and assert on generated output: every test in `tests/init_creates_file.rs` (byte-exact assertions, destination driving, error cases), plus the shared conventions across the other `tests/` files (fixture style, platform gating, binary invocation)?
