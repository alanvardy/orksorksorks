# Research Findings

## Q1: How does `init` write the initial `orksorksorks.toml` end-to-end?

### Findings
- Entry: `main()` parses and calls `run_command` (src/main.rs:82-84); `run_command` → `select_command` (src/main.rs:62-64), dispatches the `CommandResult` to text/JSON output (src/main.rs:65-74), exits 1 on error (src/main.rs:77).
- `select_command` injects an env snapshot: `select_command_with_env(cli, &ConfigEnv::from_env())` (src/commands/mod.rs:156-157).
- `Commands::Init { config }` dispatch: resolves the path, then `init_command(&path)` (src/commands/mod.rs:119-124). The `-c/--config <path>` flag is `config: Option<PathBuf>` on the `Init` variant (src/commands/mod.rs:43-48).
- Path resolution (`src/config_dir.rs`):
  - `config_file_path_with_env` (106-112): an explicit `--config` passes through byte-for-byte and never consults env; otherwise the resolved dir gets `FILE_NAME = "orksorksorks.toml"` joined on (config_dir.rs:9).
  - `resolve_config_dir_with_env` (72-96), priority: (1) `XDG_CONFIG_HOME` — used **only if absolute** (`dir.is_absolute()`, 79-80); (2) `APPDATA`, Windows-only, no absolute check (85, from_env 29-33); (3) `$HOME/.config` (90-91); (4) else `Err("config-dir", "could not determine a config directory: set XDG_CONFIG_HOME or HOME")` (93-95).
  - `ConfigEnv::from_env` reads `XDG_CONFIG_HOME` via `std::env::var_os`, `HOME` on non-Windows (config_dir.rs:26-34).
- `init_command` (src/commands/mod.rs:161-175): `create_dir_all(parent)` only when `path.parent()` is `Some` (bare relative names skip it) → `Config::default()` → `toml::to_string(&config)` → `File::create(path)` (create/truncate) → `write_all` → `flush` → `sync_all` (fsync). Only a fully-successful `sync_all` yields `Ok("✓ Created <path>")` via `format::green_string`.
- **Exact generated bytes**: `toml::to_string(Config::default())` is exactly 42 bytes, `version = "0.1.0"\nshow_frontmatter = true\n` (single trailing LF). Cause: `Config::default()` (src/config.rs:87-99) sets `version` from `CONFIG_VERSION = "0.1.0"` (config.rs:128), `show_frontmatter = true` via `default_true()` (config.rs:64, 83-86), and every vec field carries `#[serde(default, skip_serializing_if = "Vec::is_empty")]` (config.rs:67,70,73,77) so empty `[[steps/models/prompts/scripts]]` never appear.
- Error tags: `Error{message, source}` (src/errors.rs:17-23); io failures → `"io"` (errors.rs:46-53), `toml::ser` → `"toml::ser"` (errors.rs:55-62); `Display` renders `Error from {source}:\n{message}` (errors.rs:33-43); text output to stderr with leading blank line (src/main.rs:27-34), JSON `{"error":{"message":...,"source":...}}` to stdout (src/main.rs:39-49).

## Q2: How is a config parsed and validated on read-back, and what constraints does that place on a commented file?

### Findings
- `read_config` (src/config.rs:107-124): `fs::read_to_string` (missing/unreadable → `"io"`, message embeds path + source, 110-118) → `toml::from_str::<Config>` (all syntax/unknown-key errors surface as `toml::de::Error`, converted at src/errors.rs:110-115, tag `"toml::de"`) → `config.validate()` (config.rs:123). Every command entry point calls it first: src/commands/mod.rs:275, 295, 316, 366, 405.
- `#[serde(deny_unknown_fields)]` on all five types — `Step` (8), `Model` (23), `Prompt` (35), `Script` (46), `Config` (59). Any undeclared key at any nesting level is a hard deserialization error (pinned by `unknown_step_key_is_rejected_as_toml_de`, config.rs:527-537).
- `validate()` (config.rs:139-226), deterministic first-error-wins order (docs contract config.rs:135-138; determinism test config.rs:727-738):
  1. version mismatch (140-147) → `config:version`
  2. duplicate names across steps→prompts→models (156-160) → `config:duplicate-name`
  3. empty names (162-166) → `config:empty-name`
  4. empty step model (168-173) → `config:empty-model`
  5. duplicate non-empty `trigger_artifact` (175-183) → `config:duplicate-trigger`
  6. more than one default step (empty trigger) (185-200) → `config:multiple-default`
  7. every step name must exist in `prompts` (202-213) → `config:missing-prompt`
  8. every step model must exist in `models` (215-223) → `config:missing-model`
  `scripts` entries are never semantically checked (224); orphan prompts/modals/scripts are legal (config.rs:543-558).
- Parser surface of `toml 1.1.5+spec-1.1.0` (Cargo.lock:776-779; deps `toml_parser`, `toml_writer`, `toml_datetime`):
  - `#` is lexed as `TokenKind::Comment` (toml_parser/src/lexer/mod.rs:89, 191-208) and **skipped everywhere comments are legal** — whole lines or trailing after `key = value` (document.rs:196, 323, 363, 483, 508, 582; also array.rs:71, inline_table.rs:77, key.rs:34, value.rs:28). Comments carry no data and are **not retained** (`capture_trailing` is an empty no-op, document.rs:191).
  - Blank lines and whitespace similarly skipped anywhere (document.rs:323, 363) — a heavily-commented, blank-line-separated file parses identically to a dense one.
  - Input key order is free (serde sees a name→value map); headers still enforce TOML rules: no table redefinition, `[name]` vs `[[name]]` clash is a parse error (event.rs:504-509).
  - Multi-line `"""`/`'''` strings lex as dedicated tokens (lexer/mod.rs:106-110) — how `Prompt::content`/`Script::content` carry newlines.
- Round-trip is **value-equality, not byte-equality** (tests at config.rs:266-275, 344-361, 363-377): a hand-commented file loads fine, but comments/blank lines are silently lost on any `to_string`; the writer re-emits struct-field order and omits empty vecs / `None` scripts (config.rs:17, 67-77).

## Q3: Can the resolved `toml` crate emit comments, and what commented TOML already exists?

### Findings
- `toml = "1.1.5"` (Cargo.toml:17), locked `toml 1.1.5+spec-1.1.0` (Cargo.lock:776-779). Serde facade: serializer in `src/ser/` of the vendored crate (backed by `toml_writer`), parser in `toml_parser`.
- **Serializer cannot emit comments**: `grep -i comment` over the vendored `src/ser/` tree returns zero hits; output is driven purely by serialization strategy (Value/Table/ArrayOfTables/Skip, `ser/document/strategy.rs`) plus structural tokens. No API parameter, hook, or type for comments exists on the `toml::to_string` path this repo uses (src/config.rs:262, 271, 299 call it).
- `toml_writer`'s low-level formatting trait does define `fn open_comment()` (writes `#`) — `~/.cargo/registry/src/index.crates.io-1949cf8c6b5b557f/toml_writer-1.1.2+spec-1.1.0/src/write.rs:79` — but it is a transitive dependency's low-level byte layer, not exposed by `toml::to_string(&Config)`.
- `toml_edit` is **absent from Cargo.lock** (zero matches, incl. `toml++`, `tomlplusplus`, `toml-test`). The `toml` README explicitly cedes format/comment control: "For format-preserving editing or finer control over output, see [toml_edit]" (vendored `toml-1.1.5+spec-1.1.0/README.md:7`). `toml_edit-0.25.13` and `0.22.27` exist in the local registry cache (available to depend on) but are not dependencies.
- Repo TOML is **comment-free** today: the three tracked `.toml` files (Cargo.toml, rust-toolchain.toml, .config/nextest.toml) contain zero `#` glyphs; no README/docs/fixtures dirs; CI is YAML. `#` glyphs inside `tests/*.rs` all live inside `"""` content-string literals (e.g. tests/prompt.rs:51,56,90,95,207,251), not TOML comments.
- The only hand-commented TOML anywhere is the user's live config (Q4): exactly three TOML-level comments, all **full-line comment-only lines** (no trailing `key = value # note` style): `# ---------------------------` at line 51, and ` # ---------------------------` (one leading space) at lines 63 and 97 of `/Users/vardy/dev/dotfiles/orksorksorks/orksorksorks.toml`.

## Q5: How do the integration tests exercise `init` and assert on generated output?

### Findings
- `tests/init_creates_file.rs` has 6 tests, all inline (no shared helpers); file-level `#![allow(clippy::permissions_set_readonly_false)]` (line 4); uses `assert_cmd::Command`, `predicates::prelude::*`, `std::fs`.
  1. `init_creates_orksorksorks_toml_with_default_content` (11): fresh `XDG_CONFIG_HOME` tempdir (12-15), `init`, `.success()`, then **byte-exact** `assert_eq!(content, "version = \"0.1.0\"\nshow_frontmatter = true\n")` (22-26; comment at 23-24 notes the crate is binary-only so the default serialization is pinned by hand).
  2. `init_returns_success_message` (30): stdout contains `✓ Created {resolved path}` via `predicate::str::contains` (36-45); comment 40-41 — under `cfg!(test)` the child still applies color, so only the path substring (via `display()`) is asserted.
  3. `init_in_readonly_dir_returns_error_exit_code` (49): `set_readonly(true)` (52-55), `.failure()` (60), restore (62-65).
  4. `init_json_error_in_readonly_dir_shows_source_io` (69): `init -j`, asserts stdout contains `"source":"io"` (81-84); restore 86-89.
  5. `init_with_config_flag_writes_to_given_path` (93): `--config target=temp/custom.toml` while `XDG_CONFIG_HOME` points at a "hostile" dir that must be ignored (95-100); asserts `target.exists()`, `!hostile.exists()`, and the **second byte-exact** `assert_eq!(content, "version = \"0.1.0\"\nshow_frontmatter = true\n")` (104-108).
  6. `init_without_home_fails_with_config_dir_tag` (112): `env_remove` HOME + XDG_CONFIG_HOME (114-115), `init -j`, asserts `"source":"config-dir"` (118-122).
- Exactly two byte-exact content assertions exist (lines 22-26 and 104-108), both pinning the 42-byte default. No test exercises `init` against a pre-existing populated file (no clobber coverage).
- Conventions shared across `tests/model|step|prompt|script|config_validation|json_output.rs`:
  - Per-file helpers: `init_git_repo()` (model.rs:12-22, step.rs:12-22, prompt.rs:12-22, script.rs:12-22), `git_repo_on_branch()` (artifact_directory.rs:17-41, branch.rs:17-41), `git_repo()` (config_validation.rs:24-31); `write_config` variants built with `concat!` of literal TOML lines incl. required `[[models]]`/`[[prompts]]` per step (script.rs:24-26) and `"""` multi-line contents (prompt.rs:47-49).
  - Invocation: `Command::cargo_bin("orksorksorks").unwrap()` + `.current_dir(dir)` + `.env("XDG_CONFIG_HOME", ...)` when relevant; config passed as `--config orksorksorks.toml`; regression proves no fallback to CWD config without the flag (step.rs:292-301); clap usage errors pinned `.assert().code(2)` (prompt.rs:362).
  - Output: `String::from_utf8_lossy`; every test asserts no `\x1b` in stdout; text errors on stderr matched by `contains`; JSON errors on stdout carry `v["error"]["source"]` tags (`io`, `step`, `script`, `config:*`) via `assert_invalid_config` helper (config_validation.rs:8-77).
  - Platform: no `cfg!(windows)` in tests; macOS `/var`→`/private/var` divergence handled by `std::fs::canonicalize` of tempdirs (prompt.rs:308-313, artifact_directory.rs:39-43); color stripping under test in src/format.rs:5-17 (`cfg!(test)`).

## Cross-Cutting Observations
- Single source of truth: `src/config.rs` owns types, defaults, validation, and unit tests; the 42-byte default output is re-pinned by hand in two integration tests because the crate is binary-only (no lib target — tests cannot `use crate::config`).
- The parser/comments asymmetry is total: the `toml` crate **accepts and discards** comments on read but the serializer path **cannot produce them** — any commented file currently in existence (the user's live config) is hand-authored or created outside `init`.
- Generated default (`version` + `show_frontmatter` only) is structurally a tiny subset of the user's live file (full 9/2/2/9 sections, ~1269 lines); no code path other than `init_command`'s single write ever creates or rewrites the file (no migration/rewrite code exists anywhere — the only other `File::` write is inside `init_command` itself).
- Config is loaded and validated before any command action (mod.rs:275, 295, 316, 366, 405), so any change to generated content must remain parseable + validatable; validation strictly rejects unknown keys, so comments or extra keys in sections would fail `deny_unknown_fields`.
- Existing comment style signal: the user's own file already uses full-line dash dividers between sections (no trailing comments) — the only TOML-comment precedent in the wild for this project.
- Tests drive destinations exclusively via `XDG_CONFIG_HOME` or `--config`; the success/error text and JSON `source` tags (`io`, `config-dir`, `toml::ser`, `toml::de`, `config:*`) are the pinned external contract.

## Open Areas
- No code path preserves or merges an existing file when `init` runs — the tests only cover fresh destinations, and the effect of running `init` over the user's live 1269-line file (truncation via `File::create`) is untested territory.
- The mechanism for placing comments into the dotfiles-hosted live file (repo-side template vs. manual edit of the dotfiles target) was not researched — the dotfiles repo is outside this checkout; only the on-disk file was surveyed.
- `validate()` does not check `scripts` entries at all (orphan `approach` is live proof), and nothing constrains section ordering — both are permissive seams relevant to any hand-templated file.
- The exact `$HOME/.config` fallback path on this machine resolves through the `~/.config/orksorksorks.toml` symlink; whether dotfiles tooling (e.g. GNU Stow) has its own expectations was not investigated.
