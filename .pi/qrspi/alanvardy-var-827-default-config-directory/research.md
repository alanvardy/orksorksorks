# Research Findings

Crate: `orksorksorks` 0.1.0, edtion 2024, binary-only (no `[lib]` target, no `src/lib.rs`). Source spine: `src/main.rs`, `src/commands/mod.rs`, `src/config.rs`, `src/errors.rs`, `src/format.rs`; tests in `tests/`; build script `build.rs`.

## Q1: Argument parsing flow — `Cli::parse()` → `Cli` → `Commands` → `select_command`

### Findings
- Entry: `#[tokio::main] async fn main()` at `src/main.rs:91-95`; `Cli::parse()` at `src/main.rs:93`, passed straight to `run_command(cli)` (`src/main.rs:94`).
- `Cli::parse()` is **not repo code** — it is the trait-default `fn parse() -> Self` of `clap::Parser`, generated by `#[derive(Parser)]` (clap_builder 4.6.6 `src/derive.rs:29-44`; vendored under `/Users/vardy/.cargo/registry/src/index.crates.io-1949cf8c6b5b557f/`). It reads `std::env::args_os()`, and on parse error calls `e.exit()` (no `Result`). The `Result`-returning variant `try_parse_from` is used only in unit tests (`src/commands/mod.rs:83`, `:90`).
- `Cli` struct: `src/commands/mod.rs:28-35`.
  - `#[derive(Parser, Clone)]` (`mod.rs:19`)
  - Root-command attrs `#[command(name = NAME, author = AUTHOR, version = LONG_VERSION, about = ABOUT, long_about = None)]` (`mod.rs:20-26`); the identifiers are `env!` constants (`mod.rs:5-16`) fed by Cargo (`CARGO_PKG_*`) and build.rs (`BUILD_TARGET/PROFILE/TIMESTAMP`).
  - `#[command(arg_required_else_help = true)]` (`mod.rs:27`)
  - `#[arg(short = 'j', long, global = true, default_value_t = false)]` on `pub json: bool` (`mod.rs:30-31`)
  - `#[command(subcommand)]` on `pub command: Commands` (`mod.rs:33-34`)
- `Commands` enum: `#[derive(Subcommand, Debug, Clone)]` (`mod.rs:38`), single **unit-shaped** variant `Init` (`mod.rs:39-42`). No variant carries fields, so **no per-variant arg struct exists anywhere**.
- `select_command(cli: &Cli) -> Result<String, Error>`: `src/commands/mod.rs:45-49` — `match &cli.command { Commands::Init => init_command() }`. This is the only routing; `init_command` is the only handler.
- Dispatch chain: `run_command` (`src/main.rs:68-89`) reads `cli.json` (`:69`), calls `select_command(&cli)` (`:70`), wraps into `CommandResult` (`:71-84`), `output_result(&cr)` (`:85`), `std::process::exit(1)` if err (`:86-88`).
- Clap attribute behavior (derived from vendored clap 4.6.6 / clap_derive 4.6.4 source, paths under `~/.cargo/registry/...`):
  - `global = true` sets `ArgSettings::Global` (`clap_builder-4.6.6/src/builder/arg.rs:917-923`); globals propagate into subcommand matchers during parsing (`parser/arg_matcher.rs:47-84`), so `-j` works before **or after** the `init` token (confirmed by `tests/json_output.rs:4-6` using `["init", "-j"]`).
  - `default_value_t = false` generates a lazily-evaluated, once-per-process `OnceLock` block evaluating `"false"` (`clap_derive/src/item.rs:552-600`, `584-595`); presence of a default method forces `.required(false)` (`clap_derive/src/args.rs:327-334`). `bool` gets `ArgAction::SetTrue` + `BoolValueParser` (`item.rs:1158-1173`, `value_parser.rs:1672-1730`).
  - A non-`Option` subcommand field additionally applies `.subcommand_required(true).arg_required_else_help(true)` to the root (`clap_derive/src/args.rs:214-252`, `223-231`).
  - Doc comments become `.help()` (field) / `.about()` (variant).
- **Path-style argument types: none in use.** No `PathBuf`/`Path`/`value_parser`/`from_global`/`aliases`/`env` attrs anywhere in `src/` or `tests/`. For reference, clap 4.6.6 supports `clap::value_parser!(PathBuf)` (`clap_builder-4.6.6/src/builder/value_parser.rs:226-227`, `990-1034`) and `Path` via `MapValueParser` (`:2319-2321`); `OsStringPath` does not exist in clap_builder 4.6.6.
- The only global option is `json`, declared on the root `Cli`; the sole subcommand takes no args.

## Q2: What `init` does today

### Findings
- Handler: `fn init_command() -> Result<String, Error>` at `src/commands/mod.rs:52-62` (the task framing of 48-61 is off by four; verified). Statement trace:
  - `use std::io::Write;` (`mod.rs:53`) — brings in `write_all`/`flush`.
  - `crate::config::Config::default()` (`mod.rs:55`) — infallible; `Default` impl `src/config.rs:13-19` sets `version = "0.1.0"` (`config.rs:16`).
  - `toml::to_string(&config)?` (`mod.rs:56`) → `From<toml::ser::Error>` (`src/errors.rs:48-55`).
  - `std::fs::File::create("orksorksorks.toml")?` (`mod.rs:57`) → `From<std::io::Error>` (`src/errors.rs:39-46`). **Hardcoded relative literal**, resolved against the process CWD (not binary location).
  - `file.write_all(toml_str.as_bytes())?` (`mod.rs:58`), `file.flush()?` (`mod.rs:59`), `file.sync_all()?` (`mod.rs:60`) — all io → same `From<std::io::Error>`.
  - `Ok(crate::format::green_string("✓ Created orksorksorks.toml"))` (`mod.rs:61`); `green_string` = `src/format.rs:14-16`.
- Serialization: `Config` is a one-field struct `pub version: String` (`src/config.rs:8-11`), `derive(Serialize, Deserialize)` (`config.rs:7`). `toml::to_string` (toml 1.1.5, `Cargo.toml:17`) emits exactly `version = "0.1.0"\n` (trailing newline standard toml doc serialization). The committed `orksorksorks.toml` at repo root already contains exactly that (`orksorksorks.toml:1`), so running init today truncates and rewrites byte-identical content.
- Overwrite behavior: `File::create` opens `O_CREAT|O_WRONLY|O_TRUNC` — an existing file is truncated to zero before `write_all`; **no existence check, no prompt, no backup**. On failure mid-write the truncated partial file is left behind; no cleanup (no remove/unlink anywhere).
- `?` propagation: every failure converts through one of the two existing `From` impls and bubbles `init_command → select_command (mod.rs:45-49) → main.rs:70 → CommandResult (main.rs:71-84) → output_result (main.rs:85)`; text renders stderr + bell (`main.rs:36-40`), JSON renders `{"error":{...}}` on stdout (`main.rs:52-53`), then `exit(1)` (`main.rs:86-88`).
- `From` coverage: exactly two impls — `From<std::io::Error>` (`errors.rs:39-46`) and `From<toml::ser::Error>` (`errors.rs:48-55`). The io impl **never inspects `e.kind()`**; it stores `e.to_string()` (kind text is embedded in the io `Display`, e.g. "Permission denied (os error 13)"). Consequently **every** `io::ErrorKind` (NotFound, PermissionDenied, InvalidInput, InvalidData, AlreadyExists, NotADirectory, FilesystemLoop, …) is covered generically.
- Failure modes: readable/writable-CWD missing → NotFound; read-only target or CWD → PermissionDenied (exercised by `tests/init_creates_file.rs:41-56`, `:59-78`). Invalid-UTF8-in-path is **not reachable** here: the `File::create` argument is a `&str` literal (valid UTF-8 by construction; str→Path conversion infallible). No std error kind is left unconverted; the only non-io `?` is toml serialization. Any hypothetical third error type without a `From` impl would not compile at a `?` site.

## Q3: Rust ecosystem conventions for a per-user default config directory

### Findings
- De-facto platform contract: **Linux** `$XDG_CONFIG_HOME` → fallback `$HOME/.config`; **Windows** Roaming AppData (`%APPDATA%`, FOLDERID_RoamingAppData); **macOS** `$HOME/Library/Application Support` (Apple Standard Directories). Per the [XDG Base Directory spec](https://specifications.freedesktop.org/basedir-spec/basedir-spec-latest.html), unset **or empty** `XDG_CONFIG_HOME` → `~/.config`; **relative** values must be treated as invalid and ignored.
- `dirs` crate ([docs.rs](https://docs.rs/dirs/latest/dirs/fn.config_dir.html)): `config_dir() -> Option<PathBuf>`; Linux `$XDG_CONFIG_HOME` else `~/.config`; macOS `~/Library/Application Support` (v3 breaking change from `~/Library/Preferences`, v2 behavior in `preference_dir()`); Windows via `SHGetKnownFolderPath(FOLDERID_RoamingAppData)` — **does not read the `APPDATA` env var** ([dirs/src/win.rs](https://raw.githubusercontent.com/mozilla-firefox/firefox/main/third_party/rust/dirs/src/win.rs)); does not honor XDG vars on macOS/Windows; does not create directories; returns `None` when unresolvable.
- `directories` crate: `BaseDirs` (app-independent) vs `ProjectDirs::from(qualifier, organization, application)` — app name required and lowercased into the path everywhere ([docs.rs](https://docs.rs/directories/latest/directories/struct.ProjectDirs.html)); Mac/Windows add org/app segments; `config_local_dir`/`cache_dir` → LocalAppData.
- `etcetera` crate ([README](https://github.com/lunacookies/etcetera/blob/master/README.md)): caller picks the strategy — `choose_base_strategy()` gives Windows dirs on Windows, XDG everywhere else (macOS gets `~/.config`); `choose_native_strategy()` gives Apple dirs on macOS. `AppStrategyArgs { top_level_domain, author, app_name }` for app dirs. Home resolution moved to `std::env::home_dir()` in v0.11.
- `home` crate ([cargo source](https://rust.googlesource.com/cargo/+/fd1f1043e09e4bb77c808deb6244b5f8b9209f29/crates/home/src/lib.rs)): `home_dir()` — `$HOME` if set, else `getpwuid_r` (Unix) / `%USERPROFILE%` else `FOLDERID_Profile` (Windows); README now says "use `std::env::home_dir()`"; primarily Cargo/rustup-internal.
- `std::env::home_dir()` ([std docs](https://doc.rust-lang.org/std/env/fn.home_dir.html)): `$HOME` else passwd (Unix), `%USERPROFILE%` else API (Windows); Windows stopped honoring `HOME` in 1.85, undeprecated in 1.87, empty `$HOME` treated as unset. The std docs explicitly recommend "XDG Base Directories on Unix or the `LOCALAPPDATA` and `APPDATA` environment variables on Windows" for config storage rather than `home_dir()`.
- 2024–2026 migration trend: projects move **to `etcetera`** (ruff, git-cliff [PR #1477](https://github.com/orhun/git-cliff/pull/1477), testcontainers-rs [PR #736](https://github.com/testcontainers/testcontainers-rs/pull/736)) or **to direct env-var reads / `std::env::home_dir`** (uv [PR #16483](https://github.com/astral-sh/uv/pull/16483), sqlx, wasm.directory "Use XDG_CONFIG_HOME directly instead of dirs::config_dir()") and away from hard-coded macOS Apple dirs; `dirs-lite` offers a `favor-xdg-style` cargo feature; newer crates `dir_spec`, `user_dirs` are XDG-first on all platforms.
- Platform gotchas: empty-string `XDG_CONFIG_HOME` = unset per spec; relative env values are invalid per spec (Wayland enforces this); Windows `APPDATA` may be missing in CI/minimal envs, which is why Known-Folder-API crates don't read the env var; base-dir crates return `Option` so the unresolvable case (no HOME/passwd, Android sandboxes, UWP) must be handled.
- The target crate has **no** config-dir dependency today (`Cargo.toml:10-23`); this is greenfield.

## Q4: Central `Error` type and rendering

### Findings
- Definition: `#[derive(Debug, Clone, PartialEq, Eq, Serialize)]` (`src/errors.rs:9`), `pub struct Error { pub message: String, pub source: String }` (`errors.rs:10-13`). **Flat two-String struct — no enum, no kind, no severity**; `source` is a lowercase tag (`"io"`, `"toml::ser"`) per the doc comment (`errors.rs:4-8`).
- Constructor `Error::new(source: &str, message: &str)` at `errors.rs:18-23`.
- `impl fmt::Display for Error` (`errors.rs:26-35`): writes `Error from {yellow source}:\n{red message}`; coloring is applied **inside** Display via `crate::format::yellow_string`/`red_string` — callers must not pre-apply ANSI.
- `impl std::error::Error for Error {}` (`errors.rs:37`) — empty body, no `source()`/`cause()`.
- Conversions — exactly two in the crate:
  - `From<std::io::Error>` (`errors.rs:39-46`): `source: "io"`, `message: e.to_string()`.
  - `From<toml::ser::Error>` (`errors.rs:48-55`): `source: "toml::ser"`, `message: e.to_string()`.
- Rendering chokepoint (`src/main.rs`):
  - `CommandResult` wraps the result + `json` flag plus `bell_success`/`bell_failure` (`main.rs:17-26`).
  - `output_text` (`main.rs:29-42`): Ok → `println!("{data}")` (**stdout**, `main.rs:32`) + bell `\x07` via `print!` to **stdout** (`:34`); Err → `eprintln!("\n\n{e}")` to **stderr** (`:37`, two leading newlines, colored `Display`) + bell on **stdout** (`:39`).
  - `output_json` (`main.rs:45-56`): Ok → `serde_json::json!({"data": data})` on **stdout** (`:48-49`); Err → `serde_json::json!({"error": {"message": e.message, "source": e.source}})` on **stdout** (`:52-53`) — reads the **raw String fields** directly, not Display, so no ANSI in JSON.
  - `output_result` branches on `cr.json` (`main.rs:59-65`); exit code 1 on err (`main.rs:86-88`).
- Color machinery: `apply_color` in `src/format.rs:6-12` is the single ANSI chokepoint — under `cfg!(test)` it returns the string unchanged (`format.rs:7-9`). `green_string` (`:14-16`), `red_string` (`:18-20`), `yellow_string` (`:22-24`).
- What a new conversion would integrate with (what exists): it would be written in `src/errors.rs` next to the two existing impls, following the same shape `Self { source: "<lowercase-tag>", message: e.to_string() }`; there is **no match/switch over error variants** anywhere, so both render paths handle it automatically — `Display` colors the new tag/message (`errors.rs:29-30`), JSON reads the fields (`main.rs:52`), exit code via `main.rs:86-88`. The only behavioral branches are `cr.json` (`main.rs:59-65`) and `is_err()` (`main.rs:86-88`) — neither inspects error content.
- Note: `bell_success`/`bell_failure` are set in `run_command` (`main.rs:74-75`, `:80-81`) but **never read**; the bells are hardcoded inside `output_text` (`main.rs:34`, `:39`).

## Q5: Test structure and the binary-only constraint

### Findings
- Fixture strategy: `tempfile::tempdir()` (regular dep 3.27.0, `Cargo.toml:15`) creates the temp dir; `assert_cmd::Command::cargo_bin("orksorksorks")` (dev-dep 2.2.2) locates the compiled binary; `cmd.current_dir(temp.path())` (assert_cmd) redirects the child CWD. `predicates::str::contains` (dev-dep 3.1.4) is the only predicates usage (`tests/init_creates_file.rs:7`, `:37`). **No env vars are ever set on the child** (`tests/json_output.rs` does not even set `current_dir`, so those tests run in the repo root containing the committed `orksorksorks.toml`).
- Exact-location/content assertions: `tests/init_creates_file.rs:18-25` — builds `temp.path().join("orksorksorks.toml")`, asserts existence (`:19`), reads (`:21`), and asserts **exact** content `version = "0.1.0"\n` (`:24-25`). The comment at `:22-23` states the crate is binary-only so the integration test cannot import `Config`.
- Readonly-directory cases: `init_in_readonly_dir_returns_error_exit_code` (`tests/init_creates_file.rs:41-56`) and `init_json_error_in_readonly_dir_shows_source_io` (`:59-78`). Pattern: `fs::metadata(...).permissions()` + `set_readonly(true)` + `fs::set_permissions(...)` (`:43-45`, `:61-63`), assert `.failure()` / `"source":"io"` in stdout, then restore writable (`:53-55`, `:75-77`) so `tempfile` can clean up. **No platform gating** (`#[cfg(os(...))]` absent anywhere in tests); `#![allow(clippy::permissions_set_readonly_false)]` file lint at `:1-4`.
- Binary-only constraint: `Cargo.toml:1-8` has only `[package]` — no `[lib]` target, no `src/lib.rs`. Integration tests therefore **cannot import any crate item**; they assert observable stdout/exit/created-file only, while in-module `#[cfg(test)] mod tests` blocks (`use super::*`) can touch private internals: `src/commands/mod.rs:64-98`, `src/config.rs:21-39`, `src/errors.rs:57-114`, `src/format.rs:26-43`.
- Unit tests: `select_command_routes_init` (`mod.rs:70-78`) calls `init_command()` **in-process**, which writes `orksorksorks.toml` into the test-runner CWD (currently pollutes it); `cli_try_parse_*` use `Cli::try_parse_from` (`mod.rs:80-92`); config/errors/format tests are pure.
- Tests tied to the CWD write (affected if the default location moves away from CWD):
  - `tests/init_creates_file.rs:11-26` (file at CWD + exact content),
  - `:29-38` (outcome depends on CWD writability),
  - `:41-56` and `:59-78` (readonly-CWD is the failure trigger — they become meaningless if the write target is no longer the CWD),
  - `src/commands/mod.rs:70-78` (in-process write into runner CWD).
- Tests **not** affected: `tests/json_output.rs` (assert stdout only, never inspect the file); config/errors/format unit tests (no filesystem).
- Override infrastructure: **none**. No runtime env reads in `src/` (combined greeting: no `std::env`/`env::var` in src; only build-time `env!` constants `mod.rs:5-16` and `build.rs:6`/`:10`/`:11`); no CLI flag for a target path (surface is just `-j/--json` + `init`); the only redirect mechanism in tests is `current_dir` (CWD).

## Q6: Existing file/path operations and helpers

### Findings
- **The `init` write is the only production file operation in the crate**: `src/commands/mod.rs:57-60`. No production code reads files (no `read_to_string`/`File::open` in `src/`); `src/config.rs` does no I/O (serialize/deserialize only, in tests).
- Env usage: `build.rs:5-13` reads `TARGET`/`PROFILE` at build time and emits `BUILD_*` rustc envs consumed by the compile-time `env!` constants (`mod.rs:8-16`). **No runtime `HOME`/`XDG`/`APPDATA`/any env reads exist in the binary.**
- Symlink/HOME/path normalization: **nothing** — no `read_link`/`symlink`/`canonicalize`/`create_dir(_all)`/`mkdir`/`remove`/`parent()` anywhere in sources or scripts. The only path constructed in `src/` is the hardcoded `"orksorksorks.toml"` string (`mod.rs:57`). No path utility module exists.
- Committed `orksorksorks.toml` (repo root): single line `version = "0.1.0"` (`orksorksorks.toml:1`). It is referenced by doc comments (`src/config.rs:3`, `mod.rs:40`, `:51`), the write path (`mod.rs:57`), the success string (`mod.rs:61`), and assertions (`tests/init_creates_file.rs:18-25`, `tests/json_output.rs:13`, `:29`). **No loader reads it** — nothing in the binary parses it; not referenced by install/test scripts, Cargo metadata, or workflows.
- `scripts/install.sh`: `set -euo pipefail` (`:3`), `cargo install --path . --locked` (`:6`), success echo mentioning `~/.cargo/bin` is display-only (`:8`); no path computation.
- `.gitignore:1` ignores only `/target`; nothing hints at a config-dir write target.
- Dependencies (`Cargo.toml:10-23`): regular — clap 4.6.6 (derive), colored 3.1.1, serde 1.0.229 (derive), serde_json 1.0.151, tempfile 3.27.0, tokio 1.53.1 (full), toml 1.1.5; dev — assert_cmd 2.2.2, predicates 3.1.4, pretty_assertions 1.4.1; build — chrono 0.4.45. **No fs/path/dirs/home-resolution crate.**
- No parent-dir creation, symlink, or path-normalization conventions exist that a config-dir write could reuse — there is nothing there today.

## Cross-Cutting Observations
- **Edition-2024 "prelude"-style dialect** throughout: `Result<T, E>` with `Ok`/`Err` constructors, `String`, `std::`-prefixed module paths (`std::fs::File::create`, `std::io::Write`, `std::process::exit`, `std::env::args_os`), `env!` and `concat!` macros, `cfg!(test)` compile-time flag, `&dyn` trait objects, `from_utf8_lossy`. The toolchain is pinned via `rust-toolchain.toml` (channel `1.98.1`, components clippy+rustfmt).
- **Single-command CLI**: the entire surface is `init` + one global `-j/--json` flag; all components (Config, Error, format, output) exist to serve that one path. Any config-directory work slots into exactly one handler (`select_command` at `mod.rs:45-49`).
- **Write location = CWD, hardcoded**: `mod.rs:57` is the single string that pins the write location; tests redirect it only via child CWD; no override mechanism exists in code, flags, or tests.
- **Error envelope is the test contract**: JSON errors carry the `source` tag (`"io"`), and a test asserts that exact tag (`tests/init_creates_file.rs:72`); text output must have no ANSI (`tests/json_output.rs:32-35`), enforced by the `cfg!(test)` color choke (`format.rs:7-9`).
- **Truncate-then-write with no compensation**: `File::create` O_TRUNC + no existence check/backup/cleanup is a deliberate, documented-elsewhere "out of scope" posture (design note, not code).
- **Dependency discipline**: exactly 10 crates; adding config-dir resolution currently has no in-repo prior art (no env reads, no path helpers, no home resolution) and the dependency list is limited per the task framing.

## Open Areas
- **Windows behavior of the readonly tests is unasserted**: `set_readonly`/`set_permissions` come from std, but nothing documents expected Windows vs POSIX semantics (`tests/init_creates_file.rs:41-78` carry no os gating).
- **Config-directory resolution is entirely absent** from the codebase — Q3 answers the ecosystem question, but there is no existing code to point at; any un-resolvable-home/`None` handling, missing-`XDG_CONFIG_HOME`-on-macOS, and env-var-absolute-path checks are greenfield decisions with no in-repo precedent.
- Unresolved peripherals from Q3: `dirs` maintainer's macOS-XDG stance (issues #35/#56 not directly verifiable) and the no-trailing-separator claim for `SHGetKnownFolderPath` are sourced only via search synthesis.
- The `bell_success`/`bell_failure` fields (`main.rs:20-23`, set at `:74-75`/`:80-81`) are never read — observable but not explained in code.
- `cargo nextest` timing/retry behavior under `.config/nextest.toml` (retries = 2, 60s slow-timeout) is config, not evidence of observed flakiness; no claim about test flakiness is made.
